The core orchestration type is `Context` (in `internal/terraform/context.go`), which exposes `Plan()` and `Apply()` entry points. Both operations follow the same fundamental pattern:\n\n1. **Build a dependency graph** from configuration, state, and planned changes.\n2. **Walk the graph in parallel**, executing each node once all its dependencies have completed.\n3. **Delegate resource operations** to provider plugins via a gRPC-based interface.\n4. **Update state** incrementally as each resource operation completes.\n\nThe architecture deliberately separates graph construction from evaluation: graph builders transform a set of configuration and state inputs into a directed acyclic graph (DAG), and the walker evaluates that graph concurrently, with each node's execution isolated through the `EvalContext` interface.\n\n---\n\n## Graph Builder System\n\n### The `BasicGraphBuilder`\n\nThe foundation of graph construction is `BasicGraphBuilder` (`internal/terraform/graph_builder.go`). It holds an ordered slice of `GraphTransformer` values and applies them in sequence to produce a `Graph`:\n\n```go\ntype BasicGraphBuilder struct {\n    Steps               []GraphTransformer\n    Name                string\n    SkipGraphValidation bool\n}\n\nfunc (b *BasicGraphBuilder) Build(path addrs.ModuleInstance) (*Graph, tfdiags.Diagnostics)\n```\n\nThe `Build` method iterates through each `Step`, calling `step.Transform(g)` to mutate the accumulating graph. Errors from a transformer can be:\n\n- **Fatal** (`tfdiags.DiagnosticsAsError`): cause `Build` to return immediately with partial graph and diagnostics.\n- **Non-fatal** (`tfdiags.NonFatalError`): appended to diagnostics but processing continues.\n\nAfter all transformers run, `Build` calls `g.Validate()` (unless `SkipGraphValidation` is true), which checks for a single root node and absence of cycles. If validation fails, `Build` returns `nil` and the diagnostics.\n\nThroughout construction, `TRACE`-level logs capture the graph state after each transformer step when graph tracing is enabled, enabling deep diagnostic visibility into graph evolution.\n\n### The `GraphTransformer` Interface\n\nEvery transformation step implements:\n\n```go\ntype GraphTransformer interface {\n    Transform(*Graph) error\n}\n```\n\nTransformers are composable and single-purpose. The `PlanGraphBuilder` and `ApplyGraphBuilder` each define their own ordered list of transformers appropriate for the operation.\n\n### Plan Graph Construction (`PlanGraphBuilder`)\n\n`PlanGraphBuilder` (`internal/terraform/graph_builder_plan.go`) builds the graph for plan-like operations including normal planning, destroy planning, validation, and import. An empty provider block (alias-only) triggers an early return.\n- **Plan/Apply walk**: Calls `ConfigureProvider`, which evaluates the configuration block, strips marked (sensitive) values, calls `ValidateProviderConfig` on the provider instance, and then calls `Configure` to fully initialize the provider. The provider is then registered in the `EvalContext` cache.\n- **Import walk**: Uses stricter configuration validation requiring all values to be wholly known.\n\n**`nodeExternalProvider`**: For providers supplied externally (e.g., in tests or from a parent operation), this node simply registers the pre-configured instance in the evaluation context, bypassing all initialization.\n\nProvider nodes are connected as dependencies of all resource nodes that use them. The `CloseProviderTransformer` adds `nodeCloseProvider` nodes that run after all dependent resources complete, ensuring the provider connection is closed promptly. The `PruneProviderTransformer` removes provider nodes that have no resource consumers, avoiding unnecessary authentication overhead.\n\nProvider configuration propagates from parent to child modules via `graphNodeProxyProvider` nodes, which act as temporary placeholders during construction before being removed by pruning.\n\n---\n\n## State Management\n\n### State Representation (`internal/states`)\n\nThe `State` struct is the top-level container for all infrastructure state:\n\n```go\ntype State struct {\n    Modules          map[string]*Module\n    RootOutputValues map[string]*OutputValue\n    CheckResults     *checkstate.Results\n}\n```\n\n- `Modules`: Maps module instance addresses (as strings) to `Module` structs, each containing resource instances and their current attribute values.\n- `RootOutputValues`: Output values exported by the root module.\n- `CheckResults`: A snapshot of custom condition check results.\n\n`State` is explicitly **not concurrency-safe**. All concurrent access must go through `SyncState`.\n\nKey operations on `State`:\n\n| Method | Description |\n|--------|-------------|\n| `Module(addr)` | Retrieve module state or nil |\n| `EnsureModule(addr)` | Retrieve or create module state |\n| `RemoveModule(addr)` | Delete non-root module state |\n| `Resource(addr)` | Fetch resource state by absolute address |\n| `ResourceInstance(addr)` | Fetch a specific instance's state |\n| `AllManagedResourceInstanceObjectAddrs()` | List all managed resource instance addresses |\n| `MoveAbsResource(src, dst)` | Relocate resource state atomically |\n| `MoveAbsResourceInstance(src, dst)` | Move a specific instance's state |\n| `PruneResourceHusks()` | Remove empty resource containers post-destroy |\n\n### Thread-Safe State Access (`SyncState`)\n\n`SyncState` wraps a `State` with a `sync.RWMutex`, providing the same API as `State` but safe for concurrent access from multiple graph node goroutines:\n\n```go\ntype SyncState struct {\n    state *State\n    lock  sync.RWMutex\n}\n```\n\nDuring a graph walk, `EvalContext` exposes three distinct state views:\n\n- `State()`: The current (mutable) state being built during this operation.\n- `RefreshState()`: A parallel state that captures the pre-plan \"refreshed\" view of existing resources.\n- `PrevRunState()`: A read-only snapshot of the state from the previous run, used for drift detection.\n\nGraph nodes call `State().WriteResourceInstanceState(...)` to persist resource instance results as they complete, incrementally building the new state while the walk is still in progress.\n\n### State Snapshots for Concurrent Evaluation\n\nBefore initiating a graph walk, `context_walk.go` creates **deep copies** of the input state:\n\n```go\n// For plan operations:\nprevRunState = inputState.DeepCopy()\nrefreshState = inputState.DeepCopy()\n```\n\nThese copies are independent snapshots. During planning:\n\n1. `RefreshState` is updated with live values read from providers (resource refresh).\n2. The main `State` is updated with the planned new state.\n3. `PrevRunState` remains immutable, enabling drift detection by comparing `PrevRunState` vs. `RefreshState`.\n\nThis snapshot approach means each walk starts from a consistent baseline while allowing concurrent writes through `SyncState`'s locking.\n\n### State Locking\n\nState locking prevents concurrent Terraform operations from corrupting shared state. The locking contract is defined through the `Locker` interface (in `internal/statemgr`):\n\n```go\ntype Locker interface {\n    Lock(info *LockInfo) (string, error)\n    Unlock(id string) error\n}\n```\n\n`LockInfo` carries metadata about the locker (operation type, timestamp, user info) that remote backends store alongside the lock. The `LockError` type captures the lock information from a failed lock attempt, enabling Terraform to report who holds the lock.\n\n**Local backend**: Uses a `.terraform.tfstate.lock.info` file to implement advisory locking. The lock file is written atomically on lock acquisition and deleted on release.\n\n**Remote backends** (S3, Azure Blob, Consul, Terraform Cloud, etc.): Use backend-specific mechanisms—for example, S3 uses a DynamoDB table, Azure uses blob leases, and Terraform Cloud uses API-level operation locks.\n\n### The `statemgr` Interfaces\n\nThe state manager layer provides a clean interface hierarchy:\n\n```\nReader    -- RefreshState() error; State() *states.State\nWriter    -- WriteState(*states.State) error\nPersistent -- RefreshState() error; State() *states.State; WriteStateForMigration(*states.State, bool) error; PersistState(*schemas.Schemas) error\nLocker    -- Lock(*LockInfo) (string, error); Unlock(string) error\n```\n\n- `Reader` decouples reading state from writing.\n- `Writer` decouples writing to the in-memory working copy.\n- `Persistent` adds `PersistState`, which serializes the in-memory state to the backend storage (e.g., writes to disk or uploads to S3).\n- `Locker` provides distributed mutual exclusion.\n\nThe `Backend.StateMgr(workspace)` method returns an object implementing these interfaces for a given workspace, allowing the CLI to call `Lock`, `RefreshState`, use the state for planning/applying, then call `PersistState` and `Unlock`.\n\n### State Serialization\n\nState is serialized to JSON in a versioned format (`statefile.go`). The current format version is **4**. Each state file includes a `serial` (monotonically increasing integer) and a `lineage` (stable UUID identifying the state history). These two fields enable backends to detect write conflicts when multiple clients attempt to update state concurrently.\n\n---\n\n## Execution Flow and Hook System\n\n### Command Invocation to Context Creation\n\nThe entry path for both plan and apply operations starts in the command layer (`internal/command/`). For example, `command/plan.go` constructs a `backend.LocalRun` (or similar) that includes:\n\n1. Parsing flags and loading configuration.\n2. Initializing the backend and retrieving the state manager.\n3. Locking state.\n4. Creating a `terraform.Context` via `terraform.NewContext(opts)`.\n\n`NewContext` validates parallelism (defaulting to 10), stores `ContextOpts` fields, and initializes a semaphore for concurrent execution control.\n\n### The Plan Operation\n\n`Context.Plan(config, prevState, opts)` → `tfdiags.Diagnostics`\n\nInternally, `Plan` delegates to `PlanAndEval`, which:\n\n1. **Validates dependencies**: Checks that all required providers and provisioners are available.\n2. **Validates input variables**: Ensures all required variables are provided with correct types.\n3. **Applies move statements**: Processes `moved` blocks in configuration to relocate resource addresses in state before comparison.\n4. **Selects planning mode**: Routes to `plan()`, `refreshOnlyPlan()`, or `destroyPlan()` based on `PlanOpts.Mode`.\n\nInside `plan()` (normal mode):\n\n1. `planGraph()` is called, which instantiates a `PlanGraphBuilder` and calls its `Build()` method.\n2. `planWalk(graph)` executes the graph walk.\n3. After the walk, `driftedResources()` compares `PrevRunState` vs. `RefreshState` to detect out-of-band changes.\n4. `checkApplyGraph()` validates that the plan can be applied without introducing graph cycles.\n5. A `plans.Plan` object is constructed capturing all changes, drift, variable values, and status flags.\n\n`refreshOnlyPlan()` follows the same path but sets `skipPlanChanges: true`, causing resource nodes to only read current state without computing planned changes. If any resource nodes report changes, the plan returns an error.\n\n`destroyPlan()` optionally performs a refresh first, then builds a destroy-mode graph that orders all resources for deletion according to reversed dependencies.\n\n### The Apply Operation\n\n`Context.Apply(plan, config)` → `(*states.State, tfdiags.Diagnostics)`\n\nKey steps:\n\n1. **Nil/error checks**: Panics on nil plan; returns error if `plan.Errored` is true.\n2. **Variable validation**: `checkApplyTimeVariables` verifies that ephemeral variables match between plan and apply phases and that non-ephemeral variables retain plan-time values.\n3. **Graph construction**: `applyGraph(plan, config)` instantiates an `ApplyGraphBuilder` with the plan's changes.\n4. **Schema decoding**: Planned changes are decoded using provider schemas so that typed values are available during apply.\n5. **Graph walk**: `walkOperation` executes the graph with deferred operations allowed.\n6. **Check results**: Custom condition check results are recorded in the new state.\n7. **Husk pruning**: For destroy plans, `state.PruneResourceHusks()` removes empty resource containers.\n\nThe apply always returns the state—even on error—because partial application must be persisted to avoid orphaning created resources.\n\n### Graph Walking: The Walker Pattern\n\nThe parallel graph walker (`internal/dag/walk.go`) implements concurrent traversal with dependency-aware scheduling:\n\n```go\ntype Walker struct {\n    Callback   WalkFunc\n    Reverse    bool\n    changeLock sync.Mutex\n    vertexMap  map[dag.Vertex]*walkerVertex\n    // ...\n}\n```\n\nFor each vertex, a `walkerVertex` is created containing:\n\n- `DoneCh chan struct{}`: Closed when the vertex finishes (success or failure).\n- `CancelCh chan struct{}`: Closed to cancel execution if an upstream dependency fails.\n- `DepsCh chan bool`: Receives `true` if all upstream dependencies succeeded, `false` if any failed.\n\nThe walker spawns two goroutines per vertex:\n\n1. **Dependency waiter** (`waitDeps`): Monitors all `DoneCh` channels of the vertex's dependencies. Once all complete, sends `true` or `false` to `DepsCh` depending on whether any upstream failed.\n2. **Vertex executor** (`walkVertex`): Waits for `DepsCh`, then calls the callback if dependencies succeeded (or marks the vertex as cancelled if they failed).\n\nThis design allows `V*2` goroutines to run concurrently. The actual number of simultaneously *executing* graph callbacks is bounded by the semaphore in `ContextGraphWalker.Execute`:\n\n```go\nfunc (w *ContextGraphWalker) Execute(ctx context.Context, v dag.Vertex) tfdiags.Diagnostics {\n    w.parallelSem.Acquire()\n    defer w.parallelSem.Release()\n    // evaluate the vertex\n}\n```\n\nThe semaphore defaults to a capacity of 10, controllable via the `-parallelism` flag.\n\nThe walker supports **dynamic updates** via `Update(graph)`: new vertices and edges can be added mid-walk (as happens when `GraphNodeDynamicExpandable` nodes produce subgraphs), and the walker integrates them without re-executing already-completed vertices.\n\n### `ContextGraphWalker` and `EvalContext`\n\n`ContextGraphWalker` (`internal/terraform/graph_walk_context.go`) is the concrete `GraphWalker` used during plan and apply operations. It:\n\n- Holds references to all three state views (`State`, `RefreshState`, `PrevRunState`).\n- Maintains a `providerCache` (map from provider address to initialized `providers.Interface`) with a `providerLock` mutex.\n- Maintains a `provisionerCache` with similar locking.\n- Holds a `contextLock` and a `moduleContexts` cache for per-module `EvalContext` instances.\n\nWhen the walker visits a node, it calls `enterScope(moduleAddr)`, which returns a cached `BuiltinEvalContext` for that module instance or creates one. `BuiltinEvalContext` implements the `EvalContext` interface and provides:\n\n- `InitProvider(addr)`: Looks up the factory, instantiates the provider, caches it, and returns it.\n- `Provider(addr)`: Returns the cached provider instance.\n- `State()`, `RefreshState()`, `PrevRunState()`: Return the appropriate `SyncState` wrappers.\n- `EvaluateBlock(body, schema, self, keyData)`: Evaluates an HCL body in the current module scope.\n- `EvaluationScope(self, source, keyData)`: Returns an `lang.Scope` configured for the current module instance.\n- `InstanceExpander()`: Returns the `instances.Expander` for `count`/`for_each` expansion tracking.\n\n### Graph Node Types and Execution\n\nEvery graph vertex implements at least one interface to participate in the walk:\n\n**`GraphNodeExecutable`**: The most common interface for nodes that perform work:\n```go\ntype GraphNodeExecutable interface {\n    Execute(ctx EvalContext, op walkOperation) tfdiags.Diagnostics\n}\n```\n\n**`GraphNodeDynamicExpandable`**: Nodes that produce subgraphs during the walk:\n```go\ntype GraphNodeDynamicExpandable interface {\n    DynamicExpand(ctx EvalContext) (*Graph, tfdiags.Diagnostics)\n}\n```\n\nWhen the `Graph.Walk` method encounters a The core orchestration type is `Context` (in `internal/terraform/context.go`), which exposes `Plan()` and `Apply()` entry points. Both operations follow the same fundamental pattern:\n\n1. **Build a dependency graph** from configuration, state, and planned changes.\n2. **Walk the graph in parallel**, executing each node once all its dependencies have completed.\n3. **Delegate resource operations** to provider plugins via a gRPC-based interface.\n4. **Update state** incrementally as each resource operation completes.\n\nThe architecture deliberately separates graph construction from evaluation: graph builders transform a set of configuration and state inputs into a directed acyclic graph (DAG), and the walker evaluates that graph concurrently, with each node's execution isolated through the `EvalContext` interface.\n\n---\n\n## Graph Builder System\n\n### The `BasicGraphBuilder`\n\nThe foundation of graph construction is `BasicGraphBuilder` (`internal/terraform/graph_builder.go`). It holds an ordered slice of `GraphTransformer` values and applies them in sequence to produce a `Graph`:\n\n```go\ntype BasicGraphBuilder struct {\n    Steps               []GraphTransformer\n    Name                string\n    SkipGraphValidation bool\n}\n\nfunc (b *BasicGraphBuilder) Build(path addrs.ModuleInstance) (*Graph, tfdiags.Diagnostics)\n```\n\nThe `Build` method iterates through each `Step`, calling `step.Transform(g)` to mutate the accumulating graph. Errors from a transformer can be:\n\n- **Fatal** (`tfdiags.DiagnosticsAsError`): cause `Build` to return immediately with partial graph and diagnostics.\n- **Non-fatal** (`tfdiags.NonFatalError`): appended to diagnostics but processing continues.\n\nAfter all transformers run, `Build` calls `g.Validate()` (unless `SkipGraphValidation` is true), which checks for a single root node and absence of cycles. If validation fails, `Build` returns `nil` and the diagnostics.\n\nThroughout construction, `TRACE`-level logs capture the graph state after each transformer step when graph tracing is enabled, enabling deep diagnostic visibility into graph evolution.\n\n### The `GraphTransformer` Interface\n\nEvery transformation step implements:\n\n```go\ntype GraphTransformer interface {\n    Transform(*Graph) error\n}\n```\n\nTransformers are composable and single-purpose. The `PlanGraphBuilder` and `ApplyGraphBuilder` each define their own ordered list of transformers appropriate for the operation.\n\n### Plan Graph Construction (`PlanGraphBuilder`)\n\n`PlanGraphBuilder` (`internal/terraform/graph_builder_plan.go`) builds the graph for plan-like operations including normal planning, destroy planning, validation, and import. Key fields:\n\n- `Config`: The root configuration tree representing desired state.\n- `State`: Current infrastructure state snapshot.\n- `RootVariableValues`: Input variable values for the root module.\n- `Targets` / `ActionTargets`: Optional targeting restrictions.\n- `ForceReplace`: Addresses of instances that must be replaced.\n- `Operation`: Walk type discriminator (plan, destroy, validate, import).\n- `skipRefresh` / `skipPlanChanges`: Behavioral flags controlling refresh and change detection.\n\nThe `Steps()` method returns transformers in the following conceptual order:\n\n1. **Resource node creation**: Instantiate graph nodes for each resource defined in configuration.\n2. **Variables, locals, outputs**: Add nodes for all HCL expressions that feed into resource evaluation.\n3. **Orphan handling**: Discover resources present in state but absent from configuration; add destroy nodes.\n4. **Deposed instance handling**: Add nodes for instances in the deposed state (replaced resources awaiting cleanup).\n5. **Provider node injection**: Add provider configuration nodes and connect them to their consumers.\n6. **Module expansion setup**: Add nodes to expand modules with `count` or `for_each`.\n7. **Reference analysis**: Connect dependency edges by analyzing HCL expression references.\n8. **Destroy edge ordering**: For destroy operations, reverse dependency edges so that dependents are destroyed before dependencies.\n9. **Targeting filter**: Prune nodes outside the requested target scope.\n10. **Transitive reduction**: Remove redundant edges (A→C where A→B→C already exists), reducing walker overhead.\n\nThe `initPlan`, `initDestroy`, `initValidate`, and `initImport` methods on `PlanGraphBuilder` configure operation-specific node types (e.g., validation uses read-only node types that do not mutate state).\n\n### Apply Graph Construction (`ApplyGraphBuilder`)\n\n`ApplyGraphBuilder` (`internal/terraform/graph_builder_apply.go`) constructs the graph for the apply phase. It receives the planned `Changes` and `DeferredChanges` and uses them to materialize concrete resource instance nodes for the actions that were committed to during planning. Its transformer sequence mirrors the plan graph but with critical differences:\n\n- Resource nodes are created from **the plan's change set** rather than raw configuration, since the instance addresses are already fully expanded.\n- An additional **action trigger** transformer connects action nodes to the resources that trigger them.\n- **Ephemeral resource close** nodes are added to ensure ephemeral resources are cleaned up at the end of the walk.\n- Destroy nodes for instances being deleted are connected with proper ordering constraints.\n\n### The DAG Implementation (`internal/dag`)\n\nThe underlying graph is an `AcyclicGraph` that embeds a basic `Graph` and adds cycle detection and cycle-preventing semantics.\n\nKey methods:\n\n| Method | Description |\n|--------|-------------|\n| `Root()` | Returns the single root vertex (errors if zero or multiple roots exist) |\n| `Validate()` | Asserts single root and no cycles; used after construction |\n| `Cycles()` | Returns all detected cycles using Tarjan's strongly connected components |\n| `Ancestors(v)` | Returns all vertices reachable by following edges downward from `v` |\n| `Descendants(v)` | Returns all vertices reachable by following edges upward from `v` |\n| `TopologicalOrder()` | DFS-based sort where sources precede targets |\n| `TransitiveReduction()` | Removes redundant edges in O(V·E) time |\n| `DepthFirstWalk()` / `BreadthFirstWalk()` | Traversal in normal or reverse direction |\n\n`TransitiveReduction` is applied as a final optimizer: if a path A→B→C exists and a direct edge A→C is also present, the direct edge is removed. This reduces the edge count seen by the walker without changing execution ordering.\n\n### Reference Discovery (`ReferenceTransformer`)\n\nThe `ReferenceTransformer` (`internal/terraform/transform_reference.go`) wires dependency edges based on HCL expression references. It relies on two interfaces:\n\n- `GraphNodeReferenceable`: A node that *can be* referenced by other nodes; returns a list of addresses through which it can be referenced.\n- `GraphNodeReferencer`: A node that *does reference* other nodes; returns a list of `addrs.Reference` values extracted from its configuration expressions.\n\nThe transformer builds a `ReferenceMap` (a multimap from address to vertex), then for each `GraphNodeReferencer` vertex it looks up all referenced addresses and calls `g.Connect(dag.BasicEdge(v, parent))` to add the edge. Cross-module-instance references and edges involving destroy nodes receive special handling to prevent spurious cycles.\n\nTwo additional transformers attach dependency metadata to nodes:\n\n- `attachDataResourceDependsOnTransformer`: Records `depends_on` relationships for data sources, allowing them to determine whether they can be read during planning or must be deferred to apply.\n- `AttachDependenciesTransformer`: Traverses ancestor sets and attaches dependency lists to nodes, which are then used to compute correct destroy ordering.\n\n### Dynamic Expansion\n\nResources with `count` or `for_each` and modules with repetition are represented in the plan graph as *expansion nodes* (`nodeExpandPlannableResource`, `nodeExpandModule`). These nodes implement `GraphNodeDynamicExpandable`:\n\n```go\ntype GraphNodeDynamicExpandable interface {\n    DynamicExpand(EvalContext) (*Graph, tfdiags.Diagnostics)\n}\n```\n\nWhen the walker reaches an expansion node, it evaluates the `count` or `for_each` expression to determine the actual instance set, then calls `DynamicExpand` to produce a subgraph of concrete instance nodes. The subgraph is walked recursively before the parent graph continues.\n\nFor modules, `nodeExpandModule` iterates through all known parent module paths and registers the expanded instances with the `instances.Expander`, making those addresses available for downstream reference resolution.\n\nUnknown `count`/`for_each` values at plan time produce \"unknown\" registrations in the expander, enabling the planner to defer those resources if the deferral mode is enabled.\n\n---\n\n## Provider Interface and Lifecycle\n\n### The Provider Interface\n\nAll provider operations are defined in `internal/providers/provider.go` through the `Interface` type. For example, `command/plan.go` constructs a `backend.LocalRun` (or similar) that includes:\n\n1. Parsing flags and loading configuration.\n2. Initializing the backend and retrieving the state manager.\n3. Locking state.\n4. Creating a `terraform.Context` via `terraform.NewContext(opts)`.\n\n`NewContext` validates parallelism (defaulting to 10), stores `ContextOpts` fields, and initializes a semaphore for concurrent execution control.\n\n### The Plan Operation\n\n`Context.Plan(config, prevState, opts)` → `tfdiags.Diagnostics`\n\nInternally, `Plan` delegates to `PlanAndEval`, which:\n\n1. **Validates dependencies**: Checks that all required providers and provisioners are available.\n2. **Validates input variables**: Ensures all required variables are provided with correct types.\n3. **Applies move statements**: Processes `moved` blocks in configuration to relocate resource addresses in state before comparison.\n4. **Selects planning mode**: Routes to `plan()`, `refreshOnlyPlan()`, or `destroyPlan()` based on `PlanOpts.Mode`.\n\nInside `plan()` (normal mode):\n\n1. `planGraph()` is called, which instantiates a `PlanGraphBuilder` and calls its `Build()` method.\n2. `planWalk(graph)` executes the graph walk.\n3.
